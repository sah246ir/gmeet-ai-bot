# gmeet-bot

gmeet-bot is the backend of Meeting Bot — the part that never actually joins a meeting, but does everything else. It receives the live audio that the attendee bot ([`joinee`](../joinee)) captures from a call, turns that speech into written text in real time (keeping track of who said which words), saves that transcript, and makes it possible to later ask plain-English questions about the meeting and get answers grounded strictly in what was actually said.

## How it works

The service starts up two things on the same port: a small HTTP API, and a WebSocket server that the attendee bot streams audio into. It also starts a background worker process (for turning saved transcripts into a searchable index) and a shared manager object that keeps track of one live speech-recognition session per meeting. When the process is asked to shut down, it stops every one of those live sessions cleanly before exiting.

**Turning audio into text.** Each attendee bot instance opens one websocket connection here and sends two kinds of messages: a stream of small audio chunks as the meeting happens, and a single "the meeting is over" message at the end. Every incoming message is checked against a strict schema before anything happens with it, so malformed messages are rejected outright. The first audio chunk for a given meeting causes the backend to open a brand-new, dedicated real-time connection to a speech-to-text provider for that meeting specifically — configured to recognize English speech and to label each recognized word with which speaker said it. Every audio chunk after that is simply decoded and forwarded into that same open connection. As the speech-to-text provider finishes recognizing each phrase, it calls back into the backend with the recognized text, exactly when it was said, and a per-word breakdown of who said it. The backend reduces that per-word detail down to just the word and its speaker, and saves the whole phrase as a new row in the transcript database — the text, its start and end time within the meeting, and that speaker-tagged word list. (The "meeting is over" message is meant to close and clean up that meeting's speech-recognition session, but that part isn't wired up yet — today it's just logged, so sessions stay open until the whole backend process restarts.)

**Making the transcript searchable.** Saving a transcript as rows in a database is enough to look things up meeting-by-meeting, but not enough to find "the moment where budget was discussed" without already knowing the exact wording used. To bridge that gap, there's a separate background job that, given a meeting, loads every transcript row saved for it, groups them into small batches of a few consecutive phrases each, and merges each batch's text and speaker-tagged words into a single "chunk." Each chunk's text is turned into a vector embedding — a numeric representation of its meaning — using a hosted embedding model, and stored in a vector search index together with which meeting it belongs to, its time range, and its speaker-tagged words (kept as a compact JSON string, since the search index can only store simple values like text and numbers, not nested data). This background job exists and works end-to-end, but nothing currently triggers it automatically as part of a live meeting — it's ready to be enqueued (for example, once a meeting ends) but that connection hasn't been made yet, so today it's run by hand.

**Answering questions.** Given a meeting and a question, the backend turns the question into the same kind of vector embedding, searches the vector index for the handful of chunks that best match it *within that specific meeting only*, and stitches the results together into a block of context: each chunk's time range, its transcript text, and — when available — that same dialogue broken out line by line by speaker. That context and the original question are sent to a hosted large language model along with firm instructions: answer using only the supplied transcript, don't bring in outside knowledge, don't invent anything, and if the answer genuinely isn't in the transcript, say so plainly instead of guessing.

**The data model and API surface.** Behind all of this sits a small relational schema: a meeting can have many transcript segments and many background jobs, where each job has a status and a type. The set of defined job types (processing a transcript, generating embeddings, indexing into the search index, generating a summary, extracting action items) reads like the intended shape of a fuller automated pipeline, but today only the transcript-chunking job actually exists and runs — the rest are defined for the future but nothing creates or processes them yet. The HTTP API reflects that same in-progress state: there's a basic health check, an endpoint to fetch a saved meeting along with its jobs, and a `POST /meetings` endpoint intended to kick off joining and processing a new meeting that is stubbed out but not yet implemented.

There's also a self-contained manual test path that doesn't require a live meeting at all: a small hand-written sample transcript can be run straight through the chunking and indexing step and then queried through the question-answering flow, which is useful for verifying the whole pipeline works without needing `joinee` or a real Google Meet call.

## Project layout

- **`src/index.ts`** — process entry point. Creates the HTTP app, attaches the WebSocket server to it, starts the background worker, creates the shared speech-recognition session manager, starts listening, and handles graceful shutdown.
- **`src/http/app.ts`**, **`src/http/routes.ts`** — the Express app and its routes: `GET /health`, `GET /meetings/:id` (fetch a meeting with its jobs), and the not-yet-implemented `POST /meetings`.
- **`src/ws/server.ts`** — the WebSocket server: accepts connections, validates every incoming message, and routes it to the right handler by message type.
- **`src/ws/handlers/schema.ts`** — the combined schema describing every valid websocket message type.
- **`src/ws/handlers/audio-transcribe-chunk/`** — handler and schema for incoming audio chunks: creates or reuses a meeting's speech-recognition session and forwards audio into it; persists each finished phrase to the database.
- **`src/ws/handlers/audio-transcribe-end/`** — handler and schema for the "meeting is over" signal (currently a stub — see above).
- **`src/services/transcribe-manager/transcribeManager.ts`** — an in-memory registry mapping each active meeting to its own live speech-recognition session.
- **`src/services/deepgram/deepgram.ts`** — wraps the real-time speech-to-text provider's connection: configuring it, feeding it audio, and turning its raw events into a clean transcript event (text, timing, per-word speaker data).
- **`src/services/pinecone/pinecone.ts`** — embeds transcript chunks and upserts them into the vector search index; also runs similarity search over a given meeting's indexed chunks.
- **`src/services/rag/rag.ts`** — the question-answering flow: searches the vector index for a meeting, assembles the matched chunks (including per-speaker dialogue) into context, and asks the language model to answer from it.
- **`src/services/llm/llm.ts`** — a thin wrapper around the hosted language model's chat API, carrying the meeting-assistant system prompt and its ground rules.
- **`src/lib/group-transcripts.ts`** — groups a meeting's saved transcript rows into batched, embeddable chunks, merging each batch's text and speaker-tagged words together.
- **`src/lib/prisma.ts`**, **`src/lib/redis.ts`**, **`src/lib/ENV.ts`** — the shared database client, the shared Redis connection (used by the background job queue), and environment variable loading.
- **`src/queue/connection.ts`**, **`src/queue/transcribe-chunker/`** — the Redis-backed background job queue and its worker, which performs the "group transcript into chunks and index them" step described above.
- **`src/tests/constants.ts`**, **`src/tests/ragTest.ts`** — a hand-written sample meeting transcript and a manual script that runs it through chunking, indexing, and question-answering end-to-end without a real meeting.
- **`prisma/schema.prisma`** — the Postgres data model: `Meeting`, `Job`, and `TranscriptSegment`, plus the `JobStatus` and `JobType` enums.
- **`prisma/migrations/`** — the ordered history of schema changes that have been applied to the database.
- **`package.json`** — scripts (`dev`, `build`, `start`, `prisma:generate`, `prisma:migrate`) and dependencies, centered on the speech-to-text, vector search, and language model SDKs plus Prisma, BullMQ, and Express.
- **`.env`** / **`.env.example`** — local configuration. Note that `.env.example` only documents the database, Redis, and port settings — the speech-to-text, vector search, and language model API keys that `ENV.ts` also expects aren't currently listed there and need to be added by hand.
